# React frontend architecture

The client is a React 19 application built with Vite. It uses JavaScript and the existing hash routes so deployed links and API integration remain stable.

## Application layers

- `client/src/main.jsx` mounts React and registers the production service worker.
- `client/src/app/App.jsx` owns session startup, authentication redirects, route changes, and the shared application shell; `app/useAppNavigation.js` owns responsive navigation state, focus placement, keyboard trapping, and Escape behavior; `app/useAppPreferences.js` owns theme, interface-language, and number/date locale preferences; `components/AccountMenu.jsx` renders account details, language/number preferences, security navigation, and logout through controlled callbacks.
- `client/src/app/parseRoute.js` translates the current hash into a route object. Unknown paths resolve to the not-found screen.
- `client/src/app/PageRouter.jsx` uses explicit screen and settings registries. Screens load with `React.lazy` inside shared suspense boundaries that announce route loading to assistive technology; a keyed error boundary provides localized reload and home actions when a screen fails.
- `client/src/components/` contains shared shell and UI pieces such as navigation, global search, icons, and `EventTimeline`, which renders cross-module events on both the dashboard and entity-detail screens.
- `client/src/lib/` contains cross-screen API, tenant state, date, event, UI language and number/date formatting, feedback, and URL helpers. UI language (`vi-VN` or `en-US`) is stored independently from number/date formatting; the large English interface dictionary is loaded as a separate chunk only when the selected locale needs it. Shared shell, navigation, dashboard and module overview, generic CRUD screens, POS, sales returns, wholesale sales, purchasing, sourcing, inventory replenishment, stock counts, stock by location, lot expiry, lot traceability, quality holds, inventory, currency, budget, and business time settings, quality, audit, and integration operations, custom-field, role, data, module, account security, API token, and user settings, accounting period close, settlement and e-invoice workbenches, budget variance, cross-module events, campaign performance, employee performance reviews, and company-group consolidation use the shared localization helpers. Inline API errors, operation feedback, and shared CRUD confirmation/toast messages also pass through those helpers. The module registry also has localized names and descriptions for its 51 catalog entries.
- API response parsing preserves ordinary JSON numbers as JavaScript numbers and keeps values with more than 15 significant digits or unsafe integer magnitude as decimal strings, avoiding precision loss before shared Decimal helpers receive them.
- `state.js` provides `loadAll` and `loadAllResponse` for filtered, multi-page entity reads; workflow pages should use these helpers instead of writing their own pagination loops.
- When async workbench reads can overlap, their feature data hooks should use `lib/useLatestRequest.js` to ignore stale responses and prevent state updates after unmount; refresh/loading/error state remains owned by the feature data hook.
- Route screens use `useDocumentTitle()` to keep browser tab titles in sync with the current locale without tying language changes to workbench data reloads.
- `EntityListPage` owns list loading, filters, permissions, import/export and bulk actions; `EntityListToolbar` and `EntityListPager` render controlled filters/actions/navigation, and `EntityRecordsTable` renders rows with selection/navigation callbacks for the catalog-wide CRUD screen.
- `EntityFormDialog` owns generic CRUD form state, reference loading, payload normalization, validation and persistence; `EntityFormView` renders the controlled drawer fields, errors and submit actions, `EntityFieldControl` maps catalog field types to controls, and `EntityLineEditors` handles structured business lines through callbacks.
- `client/src/features/<domain>/` groups workflow screens and related dialogs by business domain. Each feature owns its workflow state and API orchestration while using shared helpers and tokens.

Feature-local English dictionaries are used for the authentication flow, approvals, agriculture, automotive, construction, CRM, contract management, ecommerce, education, LMS, events, clinic, pharmacy, hotel and housekeeping, logistics, manufacturing, nonprofit, helpdesk, communications, documents, integration hub, BI reporting, projects, payroll, performance, recruitment, professional services, real estate, restaurant, retail POS, wholesale sales, loyalty, field service, maintenance, subscriptions, wellness, utilities, and company-group consolidation workbenches, plus accounting chart-template, bank reconciliation, and entity-import screens. These dictionaries load with their lazy feature chunks and use the shared locale dictionary as a fallback. They translate presentation text while leaving permission keys, API payloads, status values, and business rules unchanged. Static checks confirm English coverage for labels currently used by the UI; they do not validate tenant-provided data or replace manual workflow and screen-reader review, which remain in the roadmap.

## Adding a screen

1. Add the workflow screen under the matching `client/src/features/<domain>/` folder with a focused page component.
2. Add a lazy import to the screen registry in `app/PageRouter.jsx`; add its URL mapping in `app/parseRoute.js`.
3. Add navigation only where the feature is enabled and the current user has permission.
4. Use the shared API/state/date/format helpers rather than recreating tenant or money rules in a screen.
5. Use semantic headings, labels, accessible names, visible focus, and the existing CSS tokens. Selectable table rows expose their selected state and use `selectableTableRowProps` so Enter and Space activate them without changing table semantics. Add reusable styles to shared components only when more than one screen needs them.
6. Keep generated `client-dist/` output out of commits. `npm run build` copies the public assets and creates deployable output.

For translations used only by a lazy-loaded feature, keep its English text map in that feature directory and use `uiTextWith()` to fall back to the shared dictionary. This keeps feature vocabulary out of the startup bundle. Shared API errors pass through `uiText()`; stable platform, accounting, automotive and integration messages use exact translations, while interpolated permission, constraint, amount-field, repair-line, account-template, request-size, HTTP-status, integration-event and connector-header messages use shared patterns. Integration errors returned in English are also localized for `vi-VN` so the integration workflow does not mix UI languages.
Wrap every user-visible literal with `uiText()` or the feature-local translator, including text chosen by conditional branches and fallback labels; raw Vietnamese JSX text will stay untranslated in `en-US`.

Run `npm run lint:translations` while changing a screen or dictionary. The check verifies that literal `uiText()` and feature `t()` calls resolve through the shared or feature-local English dictionary, and catches raw Vietnamese JSX text, accessible text attributes, and static page titles. It is part of `npm run check`.

## Styling layers

`client/public/app/styles/` loads in this order: design tokens, base/reset and utilities, reusable components, page layout, then shared workspace refinements. Components should use semantic variables (`--surface`, `--text-muted`, `--accent`) instead of hard-coded colors. The token layer also sets native control `color-scheme` for explicit light and dark themes. Responsive behavior and reduced-motion preferences belong in shared styles unless a workflow needs a distinct interaction model.
